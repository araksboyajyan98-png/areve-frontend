## 2. Как уходит заявка — решено

**Решение 18.09.2026: форма отправляется на бэкенд, письмо на Gmail шлёт сервер.**
`mailto:` из обновлённого лендинга **не используется**.

Что это значит для фронтенда:

- Форма делает `POST /api/leads` (контракт — этап 6), а не открывает почтовый клиент.
- Окно «Շնորհակալություն» показывается **только после ответа `201`**.
  Если сервер ответил ошибкой — показывается текст по `code`, а не благодарность.
- Кнопки «Ամրագրել այց» и «Հարցնել գնի մասին» **остаются в WhatsApp** —
  это отдельный от формы канал и для Армении он надёжнее почты.
- Адрес Gmail на фронтенде не появляется: он живёт в окружении сервера,
  и спам-боты его со страницы не соберут.

Ниже — почему `mailto:` отклонён; оставлено, чтобы к решению не возвращаться.

### Что не так с `mailto:`

- **Заявка теряется молча.** `mailto:` открывает почтовый клиент родителя.
  На телефоне без настроенной почты не произойдёт **ничего** — а окно
  «Շնորհակալություն» всё равно покажется. Родитель уверен, что написал;
  центр не получил ничего и даже не знает об этом.
- **Нигде не остаётся следа.** Письмо уходит из ящика родителя или не уходит
  вовсе. Списка обращений не существует.
- **Адрес почты открыт в коде страницы** — его соберут спам-боты.
- Родитель должен сам нажать «отправить» в почтовом клиенте. Многие не дойдут.

### Что даёт бэкенд

Он уже написан и проверен: заявка сохраняется, лишние запросы отсекаются,
боты ловятся, телефон приводится к одному виду, имя и телефон не попадают
в логи. Не хватает одного — уведомления (этап 6 бэкенда), и как раз его
обновлённый лендинг пытается решить через `mailto:`.

### Что осталось уточнить

- **Номер для WhatsApp.** Заглушка `wa.me/37400000000` из лендинга заменена
  на первый из телефонов центра — `wa.me/37495313633`, лежит в
  `shared/config/index.ts`. **Требует подтверждения:** если для WhatsApp
  у центра другой номер, меняется одна строка.
- **Адрес Gmail** для `LEADS_NOTIFY_TO` на сервере — центр даст позже.
  На фронтенде он не нужен.

## 3. Замечание об архитектуре

Скелет рассчитан на приложение, а лендинг — почти целиком статика: единственный
запрос к серверу за всё время визита это отправка формы. FSD тут не лишний
(виджетов десяток, и им нужны границы), но стоит понимать, что слой `entities`
будет состоять из одной сущности, а `features` — из одного действия.

Это не повод менять архитектуру: она выбрана, скелет под неё готов, проверки
работают. Просто не нужно изобретать сущности там, где их нет, — тексты остаются
текстами (см. `architecture.md`, раздел 13).

## 4. Порядок работы

1. Каждая правка оставляет `npm run check:arch` зелёным.
2. `tsc` и `eslint` без ошибок — pre-commit проверяет.
3. Новая переменная окружения — сразу в `.env.example` и `vite-env.d.ts`.
4. Новый текст — сразу ключом в словарь, **во всех** языках.
5. Новый код ошибки бэкенда — сразу перевод в разделе `errors`.
6. Списки, созданные при загрузке модуля, хранят **ключи**, а не тексты.
7. Файл, на который никто не ссылается, удаляется.

**Контракт с сервером** (описан в `docs/project-plan.md`, раздел 3, репозитория **areve-backend**):

```
POST /api/leads
{ name, phone, message?, website? }  →  201 { id }
```

| Поле | Обязательное | Ограничение |
|---|---|---|
| `name` | да | 1–100 символов |
| `phone` | да | принимаются `+374 77 123 456`, `+37477123456`, `077 123456`, `77123456` |
| `message` | нет | до 2000; пустая строка = не заполнено |
| `website` | нет | ловушка, скрыта стилями |

Коды ошибок, которым нужен перевод в разделе `errors`:
`VALIDATION_FAILED` (400), `RATE_LIMITED` (429), `INTERNAL` (500), `NOT_FOUND` (404).

В `details[].message` приходит **имя поля** (`name`, `phone`, `message`) — это
ключ перевода, а не готовый текст.

### Найденная тестами ошибка (18.09.2026)

Тест разбора телефона нашёл настоящий дефект в **обеих** реализациях:
номер на цифру короче — `095 313 63` — не отвергался, а превращался
в `+37409531363`.

Восемь цифр с ведущим нулём попадали в ветку «номер без кода страны», и ноль
уезжал в код оператора. В базу легла бы заявка с несуществующим телефоном,
по которой некому перезвонить, — а форма показала бы благодарность.

Починено: код оператора не может начинаться с нуля. Правка в обоих проектах,
тест её сторожит.

Это же объясняет, зачем тест сравнивает две реализации, а не одну: обе были
неправы одинаково, и проверка «фронтенд согласен с бэкендом» такую ошибку
не поймала бы. Её поймала проверка против ожидаемого результата.
